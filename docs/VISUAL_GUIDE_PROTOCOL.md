# Visual task guide protocol

The development app uses one Clicky-owned task and one provider process. The user performs desktop actions. Release walkthrough presentation is gated in `VisualGuideController+Turns.swift` until the native acceptance matrix passes. `ClickyCapabilities.verifiedGuidance` remains false.

## Contracts and ownership

`GuideContract` packages prompt `clicky-guide-8`, isolation profile `clicky-isolation-1`, and the shared strict JSON schema. All portable contracts are explicitly `nonisolated`. The app compiles these sources directly; it does not link another copy of ClickyCore.

`GuideAgentTurn` sends a JSON host request containing `protocolVersion`, `purpose`, `allowedKinds`, `responseContract`, `text`, optional `task`, and optional `capture` (window or display). Purposes are planning, sideQuestion, verification, continuation, recovery, and oneOffContext. Task context contains the goal, task ID, step/context revisions, current step, and milestone provenance. Images accompany the request as Claude image blocks or Codex image data URLs over stdin.

Responses are exactly one of:

| Variant | Required meaning |
|---|---|
| `context_request` | Approved window overview, or a detail crop referencing the current capture ID |
| `guide_step` | Short instruction, capture ID, pixel target, expected action, independently checkable outcome, semantic `milestone`, advisory `plan` (remaining milestone intents, at most 8) and `goalChecks` (at most 6 final-goal conditions); optional `detail`, `mark`, `value` and dim `ghost` target |
| `annotation` | Answer `text` (shown under the input), pixel target, `mark` (circle, underline, highlight, arrow, value + `value`), short `label`; points only, never progress |
| `explanation` | Readable conceptual answer |
| `clarification` | One necessary question |
| `verification_result` | Current capture ID, Boolean verdict, `outcomeState` (confirmed, contradicted, pending, unknown; only confirmed may accompany `matches: true`), concrete outcome evidence and its image-pixel `evidenceTarget` |
| `task_completed` | Fresh evidence confirming the entire goal and an `evidenceTarget` encompassing that evidence |
| `task_proposal` | Proposed distinct goal; replacement requires the host's choice |

Provider output has one root field, `presentation`, whose value is one of eight strict kind-specific objects. Each variant requires its own fields and forbids fields belonging to other kinds. Decoration fields may be null; a step's capture, target, action and outcome may not. The compact schema uses 13 union parameters; step semantic fields and the verdict's `outcomeState` are required non-null fields of their variants, so they add none. Codex receives a purpose-specific schema per turn; Claude receives the full schema at process launch and the host enforces each request's allowed kinds before normalization. Only unused fields are filled with null for the shared in-memory model after strict variant validation. Unknown fields, invalid nested objects, missing grounding, nonfinite/out-of-image rectangles, unsupported keys, stale capture IDs, and inappropriate response purposes fail closed. Responses are buffered until validation; raw JSON never reaches the UI. Targets and crops use image pixels. Expected key masks use AppKit Command/Option/Shift/Control bits; only matching key metadata is retained, never typed characters.

Validation failures expose only owned diagnostic codes and schema field paths, never rejected contents or unknown field names. Both positive and negative verification verdicts require the supplied capture UUID, nonempty explanatory evidence and the complete visible outcome region. Value-entry steps use `field_commit`, with an explicit commit key named in the instruction (normally Tab, key code 48; Return, 36, only when required). Clicking a field is not a completed value edit.

The host owns locating, waiting, verifying, uncertain, paused, completed, and canceled states. It serializes provider turns and captures. Task/step/context revisions, transaction generations, and capture leases reject late work after cancellation, replacement, movement, or revocation. Each planning request permits two evidence acquisitions, including an initial image and any detail crop. Verification permits one fresh check and one fresh recheck per episode. Per step (`GuideStepBudget`), at most 3 automatic episodes, 2 automatic re-locations and 1 automatic recovery run; these reset only when the step advances, so noise cannot renew them. Explicit Re-check is not budgeted.

The host owns a bounded semantic plan (`GuidePlan`): stable milestone identities, a revision that changes only when the route changes, and goal checks frozen from the first nonempty set so a later route cannot narrow the goal. A revised route marks dropped pending milestones superseded and never reopens completed ones. The execution ledger records verified, manually acknowledged, or `satisfied` provenance; satisfied means fresh state already showed the milestone and never claims an unseen action. Every pause carries a `GuideInterruption` reason: composer, side answer and app switch are temporary and may clear without user action; explicit pause, revocation, permission loss, lock/sleep, target closure and provider failure need a deliberate resume. Task context sent to the provider includes the stored goal checks, plan items and plan revision.

An action attempt, a verified outcome, and manual acknowledgement are separate. Next records a manual milestone. A different route can satisfy the same independently checked outcome. A `task_completed` proposal never completes the task by itself: the host sends a verification turn listing the stored goal checks (or the goal text when none were given) against a fresh capture and completes only on `matches: true`, `outcomeState: confirmed` and unchanged evidence pixels, so a reverted earlier setting blocks completion. One failed final check triggers one automatic continuation toward the remaining checks; a second leaves the task uncertain. A step still shown at verified completion is recorded as `satisfied`. Finished manually explicitly records manual completion. A side question (only while a walkthrough is visible) preserves the task and cannot produce a step or completion; it may point with an annotation. An `explanation` carrying a capture ID and valid target is normalized to an annotation. An annotation or step whose capture is stale (or whose mark falls outside the 2% edge slack) gets one automatic fresh capture before failing. Resume and Retry relocate against fresh evidence. Failed/canceled user turns restore text only.

## Sharing boundary

Quick Ask resolves the originating PID/application/window before taking focus. Opening it captures nothing and sends nothing. The popup remains beside its original opening position; it no longer tracks the pointer. Text is submitted first. A context request grants the originating window under Automatic sharing without a prompt. Off prevents sharing and the answer is text-only with a Settings hint. An explicitly attached image can still support an explanation.

Legacy Always migrates by its saved raw value to Task window. Legacy Off and Ask each time retain their intent. Saved project directories and coding-session bindings are retired. Preferences and isolated authentication persist; task content, responses, snapshots, and milestones are in memory.

A grant identifies an exact window and process. Independent capture uses `SCContentFilter(desktopIndependentWindow:)`. Established AX-related sheets, dialogs, and menus can be included through explicit window inclusion; `includeChildWindows` and shadows are disabled. A same-app unrelated window is not included. Without a reliable relationship, use Change target and explicitly select the window. There is no application-wide fallback. With no identifiable window (e.g. the desktop), the display under the pointer at ask time is bound as the task target (`WindowCaptureTarget.display`); pointer movement later cannot retarget it. Before its first capture Clicky asks once per running process for that display and provider (`GuideDisplayConsent`, in memory only). Share display creates the session grant; Text only declines that request, which then continues text-only without re-prompting. Another display or provider asks again. The persisted preference `displayFallbackAllowed` (migrated from legacy `displaySharingApproved`) only permits asking; turning it off revokes the live grant and pauses a display task. It uses the same capture envelope, observation, target guard and verification as a window; it has no AX window, so AX outcomes and field reads are unavailable and app activation does not pause it.

Capture envelopes contain capture/time, task/step/context revisions, grant, PID/application/window/display identities, included window identities, image dimensions, global top-left captured region, and pixel-to-desktop scale/translation. Detail captures have their own envelope and transform. PNG limits are 3 MiB and 4096 pixels per axis; overview sizing is at most 1568 pixels on the long side and 1.15 MP. A capture failure never silently sends text without the requested evidence.

Pause cancels queued captures/transmissions and invalidates leases. Closing/minimizing the target or activating another window pauses guidance. Returning requires fresh validation. Screen Recording is requested only through an authorized capture. Accessibility is optional: denied/custom controls use vision and manual Check now.

## Presentation

Chat answers, errors and annotation text appear under the Quick Ask input. Walkthrough instructions appear in the notch island: Step N (no model-estimated total; only the no-AI demo shows n/N), segmented progress (verified filled, user-confirmed outlined), title, detail, waiting status and ⌥⇧← back · ⌥⇧→ skip · ⌥⇧R retry · ⌥⇧⌫ end. The target carries only the mark (and a label for one-off annotations) plus the companion. Marks are drawn on one click-through panel per display above open menus; one bright mark at a time, at most one dim ghost, the label never overlaps the target and stays inside its window. Captures exclude Clicky's own windows.

Label and value plates use native text-cell measurements. Placement avoids bounded, nonsecure control frames from the exact approved AX window, plus targets and other plates. If no clear position exists, the plate is omitted; the mark and readable Quick Ask answer remain. AX-unavailable/display targets cannot supply neighboring control frames. Boundary candidates are capped at 64 coordinates per axis while retaining every obstacle in collision checks.

## Observation and freshness

Observers run only while waiting. Opening Quick Ask stops them, so composer Enter/clicks cannot satisfy a target step. Mouse matching uses recorded position, timestamp, button, and paired press/release counts. A release whose native click count is zero may inherit only its matching in-target press count; orphan, dragged, mismatched and out-of-target releases are rejected. The pixel guard waits during a matching held press and a short interaction grace period; unrelated clicks and focus changes do not consume verification attempts. Double-click steps reject the first click and use the OS interval for coalescing. Expected keys reject repeats/duplicates; other character/key data is discarded. Field reads are bounded, scoped to the approved AX tree, and exclude secure fields. Editing the expected field suspends its pixel guard and ignores value/selection notifications, including bubbled ancestor notifications; commit keys or leaving that field trigger verification without per-character captures.

A matched release is acknowledged locally ("Got it · checking") and then settles for 300 ms before verification; a double-click arrives as one count-2 release, so the system double-click interval is not added. Without an accepted attempt, AX notifications and focus changes can only trigger a local AX predicate check, never a capture or provider turn. Verification tries the step's bounded AX predicate first: if it already holds (and did not hold when the step was shown) the step is confirmed with no capture or provider call; if it is false the host shows "Waiting for the app" and polls AX every 250 ms for up to 3 s before falling back to vision. A predicate already satisfied before the step cannot itself verify that step. A `pending` verdict waits 3 s locally before the single recheck; `contradicted` or `unknown` waits 1 s. Waiting never captures, uploads or calls the model, and a timeout is never success. A contradicted result after both checks triggers one automatic recovery turn that inspects the current state (detour or user ahead) without claiming unseen actions; otherwise the step becomes uncertain while its mark and observer stay armed, so a new genuine attempt starts a new bounded episode without Retry.

The target guard compares the target's pixels every second using local captures only. Hover and press feedback are expected: comparisons are skipped while the pointer is within 12 pt of the target, during a held press or field edit. A change must persist for two consecutive checks with the pointer away before it counts as replacement. Replacement, window move/resize, field geometry change or scroll re-grounds the same semantic step against fresh evidence ("Finding the control") within the relocation budget; no milestone is recorded. Pixel comparisons never establish success. No pointer-driven, per-character, or periodic cloud screenshots occur. Provider verdicts and final completion are checked against a new local capture before acceptance. Uncertainty keeps the annotation and observer on an unchanged window and offers Re-check.

Pixel comparisons capture the original context region at its original output dimensions, then crop the same integral pixel rectangle. Independently resampling a target crop is not equivalent and must not be used as a freshness comparison. Waiting marks permit the documented 2% edge slack; verdict evidence must be wholly inside the image, without clipping. Verification and completion compare exact pixels across the provider's `evidenceTarget`, which must encompass all visible evidence supporting the outcome, rather than comparing unrelated clocks, recording indicators or background windows. Missing/out-of-image regions fail closed. Capture IDs, task generations, window identities, focus and geometry remain mandatory; matching a region alone never establishes success. Focused field identity and geometry remain checked while editable pixels are changing. Display-sharing revocation pauses an active display task, invalidates pending work, and prevents resume/transmission until consent is restored.

The target circle/companion stay click-through. Separate nonactivating controls provide Check now, Retry, Next, Pause, scope changes, and End. Pause/End remain usable during active requests. Checklist/sharing details are collapsed by default. They show the exact window, last transmission, and manual/verified provenance. The no-AI demo uses deterministic fixtures, performs no capture, and never claims real outcome verification.

## Provider isolation

Clicky's requested defaults are Claude `claude-haiku-5-5` and Codex `gpt-6-luna`, both at `low` effort. The user may raise effort for one prompt (Quick Ask ⌥⇧E); follow-up checks, retries and manual Next run at `low`. Claude receives explicit model/effort flags at process launch, so a running task keeps its launch effort; Codex receives process configuration (audited at `low`), thread model and per-turn model/effort. Model access failures are visible and never trigger substitution. Model IDs/effort support: [Claude Haiku 5.5](https://platform.claude.com/docs/en/models/haiku-5-5/overview), [Claude effort](https://platform.claude.com/docs/en/build-with-claude/effort), [GPT-6 Luna](https://developers.openai.com/api/docs/models/gpt-6-luna).

Claude uses normal authentication, safe mode, empty setting sources, owned settings/system prompt, no tools except the schema adapter, strict MCP, disabled slash commands, and no session persistence. Debug output is directed to `/dev/null`. Preflight audits file/drop-in/remote-cached/MDM policy. Read-only control requests inspect effective settings before each user/image submission. Hooks, helpers, custom instruction sources, and incompatible settings block the backend. Claude's three bundled plugin metadata entries are allowed; custom plugins are rejected. Builtin agent names do not grant execution tools. CLI upgrades require compatibility and marker revalidation.

Codex uses a dedicated child `CODEX_HOME`, official ChatGPT sign-in, owned working directory, explicit base/developer instructions, ephemeral thread, and per-turn output schema. Strict configuration disables instruction discovery, memories, hooks, plugins/apps, shell/exec, browser/computer use, delegation, image/file tooling, and unrelated capabilities. Effective configuration and empty instruction-source diagnostics are required. Host-discovered skills are enumerated separately, disabled in the owned configuration and thread overrides, and configured MCP servers are disabled per thread. Approval/tool requests are declined. Authentication is never copied from a personal Codex profile or extracted by Clicky.

Every owned configuration override must match. Before any user turn, complete runtime feature diagnostics must also agree with each owned feature restriction. Missing, duplicate, paginated/incomplete, or contradictory diagnostics prevent the thread becoming ready. `node scripts/audit-codex-isolation.mjs /absolute/path/to/codex` runs a temporary unauthenticated audit with no inference and removes its profile afterward. A version allowlist entry alone does not bypass these checks.

The process/conversation remains alive across task steps and side questions. Only an active provider turn has a five-minute timeout. Local waiting has none. End closes the process. Unexpected loss requires explicit Retry into a fresh session with the in-memory task context; the submitted prompt is never automatically replayed. `clicky-guide` tests this runner and prints presentation kinds only. `clicky-text` remains a legacy diagnostic and is not the app's guide runner.

Local memory-only behavior is separate from provider retention after transmission. Native real-provider storage/isolation acceptance must verify the absence of prompt/image transcripts after each CLI/profile/prompt upgrade. Turn IDs correlate provider results; stale results cannot finish another request. Owned task files are removed after child exit rather than while it can still write.

## Validation and release

Run `bash scripts/test-core.sh` (use `--disable-sandbox` if the host already sandboxes SwiftPM and nested sandbox creation is denied), `bash scripts/typecheck-app.sh`, and `bash scripts/typecheck-app.sh --debug`. The typecheck script uses a temporary Sparkle declaration stub, so it does not replace a real Xcode build. On macOS, `test-core.sh` also compiles the production coordinator (`VisualGuideController*`, `GuideObserver`, `GuideEnvironment`, `ScopedAccessibility`, `WindowSnapshotCapture`) as SwiftPM target `ClickyGuideNative` and runs `ClickyGuideNativeTests` against a fake clock, synthetic screen, fake Accessibility and a scripted provider. These coordinator tests exercise real ordering, cancellation and late-callback rejection; they do not deliver native events, focus or captures and are not GUI or real-provider evidence. Build/run/test using Xcode's shared legacy scheme only; never terminal `xcodebuild`.

The native matrix and current evidence are in [MAC_VALIDATION.md](MAC_VALIDATION.md). Plane remains authoritative for product decisions and future work; this document describes the version-specific implementation, not a backlog.
